# ADR 0005: Snippet-anchored location correction

## Status

**Accepted (2026-10-19).** Implemented as item B2 of the OCR-borrow × AACR-Bench roadmap (iteration 1, PR `feat/b2-snippet-anchored-location`); accepted at merge, and amended only with benchmark evidence (M1 anchor metrics).

## Context

pir validates a `record_candidate` anchor only by shape: positive integers, `endLine >= startLine`, and a range that fits inside the pinned head file (`src/tools/collector-tools.ts`, `validateLocation`). The line numbers themselves are the model's word, and nothing in the pipeline ever checks that the text the claim is about actually lives there. The companion research document calls this the comment-positioning gap (`docs/ocr-borrow-and-aacr-benchmark-context.md` §3): a finding can be technically sound and still point at the wrong lines, which costs review attention and corrupts any location-based metric — including AACR-Bench's file-level semantic coverage, whose per-comment judge call is anchored by the reported path and lines.

OCR solves this by never letting the model choose lines: the reviewer supplies an `existing_code` snippet and the position is computed locally. Its three-tier chain lives in `internal/diff/resolver.go` (`ResolveComment` :62, `RelocateAcrossFiles` :100). Tier 1 is a same-file sliding-window match over normalized lines ("TrimSpace, strip `+/- ` prefixes, skip blanks"), falling back from the hunk to the whole file; tier 2 relocates across files only on a unique string hit ("zero or multiple hits are both rejected"); tier 3 asks the model for a verbatim copy as a last resort. The normalization exists because the model copies snippets from rendered diffs: leading `+`/`-` markers, indentation and blank lines are sloppy by nature, while the code text itself is not. The viewer-side rule completes the stance — when the gutter cannot be trusted, show no gutter, because a wrong gutter is worse than none.

pir's LLM-facing surface is different in one decisive way: the model already writes the candidate's prose (title, claim, trigger) through a structured tool, so an excerpt is one more optional field, not a new protocol. What pir must preserve is the rest of the loop: the tool-boundary validation contract (errors come back to the model as tool text so it can resubmit — the same retry-then-fail behavior `record_candidate` already has for malformed anchors), the byte-stable no-excerpt path, and the evidence gate that already constrains cross-file drift by requiring verdicts to cite pinned reads.

## Decision

1. **The excerpt is optional, on the anchor, and adoption is gradual.** `SourceAnchor` (`src/core/types.ts`) gains optional `excerpt`, `lineCorrected`, `originalStartLine` and `originalEndLine` fields; `CandidateFinding.anchors[]` carries them through unchanged. No excerpt means the existing validation path runs verbatim — same tool output, same stored anchor object, no new events. Nothing forces a caller or a stored row to migrate.
2. **A present excerpt is located locally and overrides the model's lines.** In `record_candidate`, an anchor excerpt runs through a normalized sliding-window match against the pinned head content (merge-base only for files entirely deleted at head — the fallback `validateLocation` already documents). Normalization is OCR's tier 1 exactly: trim each line, strip one leading `+`/`-` diff marker, drop blank lines; internal whitespace is left alone, because the model is asked to copy the line text verbatim and loosening further only adds ambiguity. The match must be a **unique** contiguous window: the located range replaces `startLine`/`endLine`, the model's range is kept as `originalStartLine`/`originalEndLine`, and the anchor is flagged `lineCorrected: true`. Nothing is silently lost, and the model's numbers are deliberately not bounds-checked against the file when an excerpt decides the range — drift that pushes them past EOF is exactly the failure being corrected.
3. **A locate failure is a tool-boundary error, not a silent correction.** Zero hits and multiple hits both return the existing `ERROR: ...` tool result, naming the path and telling the model to include more context (or to omit `excerpt` and fall back to line numbers). The model resubmits within the existing retry-then-fail contract; no wrong range is accepted and nothing throws out of the tool. Because the event is emitted only after every anchor has validated, a failed candidate never produces a spurious correction record.
4. **No cross-file relocation.** OCR's tier 2 exists to reposition comments across the diff's files; pir's evidence gate and the single-reviewer-session model already constrain drift, and a cross-file guess would let a snippet silently retarget a finding at a file the model never analyzed. Tier 1 only: the excerpt locates, or the resubmission happens.
5. **The correction is observable and consumable.** Every override emits a `line-corrected` run event (session-scoped, per anchor, carrying both ranges) so live viewers and audit tooling can count corrections; the web event consumer ignores unknown kinds, so no consumer breaks. `FindingView` gains a top-level `lineCorrected` boolean plus the per-anchor fields, so the envelope exposes the flag without a schema bump. M1 normalization can then report "correction rate among excerpt-bearing anchors" separately from "overall anchor validity" (risk R7) — excerpt-bearing and non-excerpt findings stay distinguishable in both directions.
6. **The reviewer prompt requests an excerpt and demotes line numbers.** `reviewerPrompt` asks for a few verbatim lines copied from the pinned head side of the changed file, states that the local match decides the reported lines, that a snippet not matching exactly once is rejected, and that line numbers are a fallback used only when no excerpt is supplied. Audit mode is deliberately untouched in this PR: its `record_candidate` accepts excerpts through the same code path, but its prompt is a separate adoption decision (the same gradual-adoption logic).

## Consequences

- **Positive:** reported anchors are checked against the code they describe, so a drifted line range can no longer survive into the envelope, memory, or a location-based benchmark. The failure mode is loud and cheap: the model gets a targeted error and one more attempt. The metric plumbing (flag + event) is in place before M1 needs it, and the no-excerpt path is byte-identical, so the change is invisible until the prompt starts asking.
- **Negative:** an excerpt costs prompt tokens and a locate pass per anchor; a near-miss excerpt (typo, reordered lines within a multi-line snippet, a file edited between read and record) is rejected rather than approximated, which costs a round trip. A one-line excerpt that repeats in a file (a lone `}`, a common `return null;`) is ambiguous by construction and must be widened by the model — the unique-hit rule is the price of never reporting a wrong line.
- **Neutral:** the correction fields are additive JSON inside the existing `findings.anchors` TEXT column, so no migration is needed and old rows simply lack them. `lineCorrected` means "the local match decided this anchor's lines", not "the lines changed": a model that already guessed correctly still gets the flag, and consumers that want actual displacement compare `startLine` against `originalStartLine`.
- **Follow-ups:** audit-mode prompt adoption; a per-run correction counter in the manifest if M1 shows the event stream is an inconvenient source; tightening normalization (case, internal whitespace) only with data showing it recovers matches a unique-hit rule still approves.
